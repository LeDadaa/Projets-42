## Procedure v2

## 0 escape

`entrypoint.sh` runs `alembic upgrade head` under `set -e` *before* uvicorn, and the service is
`restart: unless-stopped`. So a broken migration means the container never finishes booting, and:

```
Error response from daemon: Container ... is restarting, wait until the container is running
```

`exec` is unusable exactly when needed. Get a shell that **bypasses the
entrypoint** — starts `db` via `depends_on`, keeps the bind mounts, venv already on `PATH`:

```bash
docker compose -f srcs/docker-compose.yml -f srcs/docker-compose.dev.yml run --rm --entrypoint sh api
# then: alembic current / alembic history / alembic upgrade head ...
```

Fix the file (it is bind-mounted, so host edits are live), then `make dev` normally.

## 1 Write the model, then register it

Add the import **and** the `__all__` entry in `app/models/__init__.py`. A model that is not
registered is absent from `Base.metadata`, so alembic does not see it and proposes to
**`drop_table`** it

## 2 `alembic current` must equal `alembic heads`

```bash
docker compose -f srcs/docker-compose.yml -f srcs/docker-compose.dev.yml exec api alembic current
  # revision the DB is on
docker compose -f srcs/docker-compose.yml -f srcs/docker-compose.dev.yml exec api alembic heads
  # more than one line = branched history, must be merged
```

Autogenerating while the DB is behind head diffs against the wrong baseline and produces nonsense.

## 3 Autogenerate

```bash
docker compose -f srcs/docker-compose.yml -f srcs/docker-compose.dev.yml exec api alembic revision --autogenerate -m "<new>"
```

One topic per revision, and a message that describes this revision.

## 4 Read the generated file before applying, every time

- alembic filters its `*columns` args down to `Column` / `Constraint` / `Index` instances and
  silently discards anything else, so Postgres receives `CREATE TABLE t ()` — a legal zero-column
  table — and the error only surfaces later, on the first statement that touches a column.
- **No unexpected `drop_table` / `drop_column`**
- **Wrap every constraint name in `op.f(...)`.** Alembic copies the `naming_convention` from
  `Base.metadata` into the throwaway `MetaData` it builds for migration ops, and the `ck` template
  contains `%(constraint_name)s`, so a bare string gets the convention applied a *second* time:

  ```python
  op.create_check_constraint("ck_users_role", ...)          # -> ck_users_ck_users_role
  op.create_check_constraint(op.f("ck_users_role"), ...)    # -> ck_users_role
  ```

- **Write `downgrade()` in exact reverse order of `upgrade()`.**

### What autogenerate cannot see, and what it gets wrong

| Thing | Behaviour | What to do |
|---|---|---|
| `CREATE EXTENSION citext` | never emitted | prepend by hand before `create_table('users')` |
| enum CHECK from `enum_column()` | `include_object` in `migrations/env.py` filters out *reflected* check constraints, so drift is **never** reported — adding an enum value autogenerates an empty migration | drop/recreate the CHECK by hand; verify names in psql, not in the diff |
| enum CHECK on a **new** table | emitted automatically by `CREATE TABLE`, because `sa.Enum(..., create_constraint=True)` carries it | do *not* write it separately, you would get a duplicate |
| expression index (`LEAST/GREATEST`, `lower(...)`) | alembic **does** reflect it and proposes `drop_index` on every run unless the metadata declares it too | declare it in `__table_args__` with `text()` compiling to exactly the SQL the migration emits — see `Friendship.uq_friendships_canonical` |

## 6 Prove it — the autogenerate must come out empty

If migration and models agree :

```bash
docker compose -f srcs/docker-compose.yml -f srcs/docker-compose.dev.yml exec api alembic revision --autogenerate -m "verify_empty"
cat srcs/backend/migrations/versions/*verify_empty.py   # upgrade/downgrade must be just `pass`
rm srcs/backend/migrations/versions/*verify_empty.py    # it is a test, not a migration
```

Anything other than `pass` is drift — fix it *now*, before it compounds. Then check in psql what
actually landed, since CHECK constraints never show up in the diff:

```bash
docker compose -f srcs/docker-compose.yml -f srcs/docker-compose.dev.yml exec db sh -c 'psql -U "$(cat /run/secrets/POSTGRES_USER)" -d "$POSTGRES_DB"'
```

```sql
\d <table>   -- column types, PK/FK names, ON DELETE, indexes, CHECK constraints
```

Then exercise the constraints with real rows inside a `BEGIN; ... ROLLBACK;` — a constraint you have
not seen reject a row is a constraint you have not tested.

## 7. Round-trip

A migration you cannot reverse is half-written:

```bash
docker compose -f srcs/docker-compose.yml -f srcs/docker-compose.dev.yml exec api alembic downgrade -1 && docker compose -f srcs/docker-compose.yml -f srcs/docker-compose.dev.yml exec api alembic upgrade head
```

## Two facts worth internalising

- **A failed migration leaves the DB untouched.** Postgres has transactional DDL and alembic wraps
  the upgrade in one transaction, so a crash-looping api after a bad migration means the database is
  intact, not half-migrated — `\dt` will show nothing at all rather than a partial schema. (Exception:
  non-transactional DDL such as `CREATE INDEX CONCURRENTLY`.)
- **Edit a revision in place only while it has never been applied anywhere you cannot reset.** Once a
  revision has run on a database you cannot wipe, it is frozen: correct it with a **new** revision on
  top instead.

## Dev-only reset

Valid only while the branch is unmerged and holds no real data — wipes the `pgdata` volume so the
next boot replays the whole chain from base:

```bash
make clean && make dev
```
